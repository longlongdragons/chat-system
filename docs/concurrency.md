# 高并发与性能：设计原理、实施记录与压测数据

> 本文回答：本项目如何应对高并发？性能还能怎么提升？需不需要"多线程"？
> 所有结论都有源码依据和实测数据；优化方法注明借鉴的开源项目出处。

## 〇、先纠正一个概念：Go 里不谈"多线程"，谈 goroutine

**问"要不要多线程"在 Go 里是个伪命题**——Go 程序天然就是多线程的：runtime 维护一个 M:N 调度器，把成千上万个 goroutine 调度到少量 OS 线程上（默认等于 CPU 核数）。你写的每个 goroutine 都会自动利用多核。

本项目早已是"高并发"结构，只是你可能没意识到：

| 位置 | 并发结构 | 出处 |
|---|---|---|
| `ws/conn.go` | 每条 WS 连接 2 个 goroutine（readPump / writePump），读写互不阻塞 | 这是 gorilla/websocket 的标准模式，goim/OpenIM 同样如此 |
| `ws/handler.go` Dispatch | 每帧消息处理带 8s 超时的独立 goroutine | 防止慢请求阻塞读循环 |
| `audit/audit.go` | 后台 goroutine 每秒/64 条批量落库 | 审计永不阻塞业务 |
| `hub.go` StartSubscriber | 常驻 goroutine 消费 Redis 广播 | 跨节点投递 |

**所以正确的问题不是"要不要多线程"，而是：这些 goroutine 之间的共享数据结构有没有锁竞争？热路径上有多少网络往返？** 这正是本次优化的靶点。

## 一、调研：优秀开源项目怎么处理高并发

### 1. goim（B站，7.4k★）— [internal/comet/bucket.go](https://raw.githubusercontent.com/Terry-Mao/goim/master/internal/comet/bucket.go)

连接层的经典。核心手法：**Bucket 分桶**——把全局连接表拆成多个 bucket，每把锁只管一个桶，连接/断开只锁住 1/N 的连接集，其余桶的推送照常进行。另外房间广播用固定数量的 worker channel（`routines`）消化，避免广播风暴打爆单 goroutine。

### 2. Open-IM-Server（14k★）— msggateway / msgtransfer 分离

网关联接层只维护连接；消息投递走 msgtransfer 异步消费 MQ。**ack 在落库后即返回，投递异步化**——ack 延迟只反映持久化耗时，与群大小解耦。

### 3. tinode/chat（13.5k★）

确认了我们已实现的 seq 分配、client_msg_id 幂等是主流做法，无需推翻。

## 二、本项目热路径分析（优化前）

发一条群消息的同步链路（全部堵在发送方的 ack 之前）：

```
校验 → 敏感词 → 幂等 → 分seq → 落库 → 更新会话
  → 查成员（1次DB）
  → 逐成员查在线状态（N 次 Redis 往返！100人群=100次）
  → 逐离线成员写离线表（M 次 DB 往返！）
  → Redis 发布广播
```

两处放大器：**串行 N 次网络往返**（goim/OpenIM 绝不会这么做）+ **扇出堵在 ack 路径上**。

## 三、实施的三项优化

> 每项都按「怎么做 → 为什么 → 用什么技术 → 效果」记录。

### 优化 1：Hub 连接注册表分桶锁（`ws/hub.go`）

- **怎么做**：`users map` 从一把全局 RWMutex 拆成 32 个桶，每桶独立锁；连接按 `userID % 32` 归桶；总连接数改 `atomic.Int64`（超限回滚，无需全局锁也能硬限）。
- **为什么**：单写锁下，任何用户上下线都会阻塞全节点所有推送。分桶后写操作只阻塞 1/32 的连接集——锁竞争概率随桶数线性下降。
- **什么技术**：锁分片（lock sharding）+ 无锁原子计数。goim 用哈希分桶（其 key 是字符串），我们用整数取模——userID 是自增主键天然均匀，取模 O(1) 无哈希开销。
- **在项目中的作用**：万级连接、频繁上下线场景下，推送延迟不再被注册/注销尖刺拖住。
- **效果**：子代理用并发冒烟测试验证（50 goroutine 抢 10 个连接名额，恰好拒绝 40 个，原子计数精确）。本机压测规模下该项是"容量型"优化，延迟数字主要受优化 2/3 影响。

### 优化 2：fanout 批量化（`presence/store.go`、`conversation/repo.go`）

- **怎么做**：
  - `AreOnline`：go-redis **Pipeline** 把 N 个在线状态查询打包成**一次网络往返**；
  - `InsertOfflineBatch`：`INSERT ... SELECT unnest($1::bigint[])` 把 N 条离线记录变成**一条 SQL**；
  - 批量失败时回退到逐个处理的老路径（可靠性不降级）。
- **为什么**：100 人群原来要 ~200 次串行往返（每次 RTT 0.3~1ms，累计可达几十 ms），是 ack 延迟的最大构成。
- **什么技术**：Redis Pipeline（批量打包，非事务但读场景足够）+ PostgreSQL unnest 数组批量插入。选它们是因为：不改架构、不加组件，纯客户端能力，收益立竿见影。
- **效果**：见压测对比。

### 优化 3：ack 与扇出解耦（`message/service.go`）

- **怎么做**：消息落库、会话更新完成后立即返回 ack；扇出在独立 goroutine 异步执行（10s 超时、recover 兜底）。
- **为什么**：ack 的语义是"服务端已持久化"，不该让发送方等待投递过程；群越大收益越大（ack 延迟与群规模解耦）。
- **代价与兜底**（已写入代码注释）：① 落库到扇出完成之间网关崩溃会丢在线帧——由客户端 `sync.pull` 按 seq 缺口补拉兜底，最终一致；② 同会话并发消息的推送顺序可能与 seq 轻微乱序——前端本来就按 seq 排序渲染。

## 四、压测对比（同机同环境，100 在线连接 / 群发 50 条）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| ack 延迟 avg | 18.4ms | **8.2ms** | **-55%** |
| ack 延迟 p95 | 22.3ms | 21.8ms | 持平（p95 由 DB 写抖动主导） |
| 发送吞吐（串行） | 54 msg/s | **121 msg/s** | **2.2 倍** |
| 扇出扩散（首达→末达） | 4.0ms | 3.8ms | 持平（本机 Redis 本就很快） |
| 送达完整性 | 100/100 连接 | 100/100 连接 | 无损 |

解读：ack 延迟砍掉的一半以上来自"扇出移出同步路径 + 在线判断批量化"。群越大（500/1000 人），优化前串行往返越多，差距会成倍放大——本测试 100 人已属保守。压测脚本：`tools/ws-bench.mjs`（本地铸 RS256 令牌 + 100 并发连接，可重复执行）。

## 五、为什么我们不做这些（常见误区）

- **"上线程池/goroutine 池"**：连接 goroutine 是长生命周期的，池化无意义；goroutine 本身比线程池里的线程轻量几个量级（初始栈仅 8KB）。goim 百万连接也是每连接 goroutine。
- **"上 Kafka/MQ 削峰"**：当前单消息同步落库 + 批量扇出已到 121 msg/s 串行（并行发送会高得多）；MQ 解决的是"下游 DB 扛不住写入"，触发条件见 `docs/performance.md`。
- **"换 C10M 框架"**：Go netpoll 本身就是 epoll 事件驱动，单机万级连接是基本功。

## 六、后续触发式路线（摘自 performance.md）

1. 消息 INSERT 异步攒批（DB CPU 饱和时）
2. `chat.broadcast` 按 userID hash 分片（网关 >10 实例时）
3. messages 表按 conversation_id 分区（>5 千万行时）
4. 热点大群扇出改队列 + 离线表改游标懒加载（单群 >5000 人时）
